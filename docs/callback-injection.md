# Callback sender injection

Both bridges use the same code-only injection names:

- `makePublicRequester({ managedAdapter })` accepts the compatibility adapter shape with exactly one own data property, `send(target, request)`. This shape does not grant a managed transport capability; the default shared transport rejects configured proxy egress even when this function is present.
- `makePublicRequester({ callbackTransport })` takes a callback transport function. Its optional `preflight()` is projected into the closed callback status schema; absent or malformed status stays unverified.
- `managedCallbackAdapter` and `callbackSend` are compatibility aliases. Conflicting aliases, simultaneous adapter and transport overrides, unknown option names, and malformed objects throw fixed errors before request construction. Repeating the identical object under both alias names is accepted.

These are dependency injection interfaces in this project. They do not identify an official installed proxy component. No reviewed general-purpose managed callback implementation is supplied here. With an existing supported proxy, arbitrary `managedAdapter` / `managedCallbackAdapter` injections remain `blocked/proxy_policy_unverified`, with `destination_binding: unverified` and `network_checked: false`; DNS, request construction and adapter invocation do not run. The old `managed/delegated_unverified` status is not accepted by the closed status schema. An injected status or `ready: true` is not evidence of working network transport.

The launcher calls `createServiceSender({ proxyEnv, requesterFactory })` once. Its default is `makePublicRequester`; a reviewed launcher may supply a statically imported code factory. The factory receives `{ proxyEnv }` and returns the sender function. No environment flag, module path, arbitrary import, credential, or permission switch selects a factory. Injecting an adapter into this default requester does not unblock existing proxy configuration. A future general-purpose managed path requires a concrete reviewed implementation that binds final public-address validation to the actual dial, while preserving hostname policy. The existing direct pinned path remains available in environments without a proxy.

The separately imported `experimental/owner-message.js` transport is an explicit, time-bounded owner experiment. Its active status is `owner_single_message_proxy`, with `destination_binding: unverified` and `network_checked: false`. It requires explicit experiment approval, one channel and a deadline of at most 15 minutes; it binds a single callback and subscription, allows one challenge attempt and one owner event attempt, and does not retry. Owner/provider identity and subscription authentication remain upstream. No default requester or service launcher selects it. Its status does not attest the proxy's final destination address or make the general managed path ready.

Pass the returned `send` to the service and its preflight. The service forwards that exact function into the app and the selected Sites runtime. Callback challenge and queued event dispatch both use the app's sender. Provider request routing and provider/callback budgets retain their existing defaults.

All plan and unconfirmed branches return before sender or credential construction. Configuration checks are local configuration inspection, and can read approved credential file references when they validate configuration; they never establish network readiness.

QQ formal wiring lives in `scripts/qq-service.js`: `servicePreflight(env, { send })` reads callback state from that sender, then `startLockedPersistentService(config, { send, ...options })` forwards it through `startPersistentService` to `createApp`. Keep the same sender for repeated preflight calls; never recompute callback transport from the environment independently. `src/main.js` uses this same entrypoint. A standalone `servicePreflight(env)` constructs an inspection sender and does not start a service.

Offline verification: `node --test --test-concurrency=1 test/callback-transport.test.js test/requester-injection.test.js test/service-runtime.test.js test/service-mode-lock.test.js test/network-auth.test.js`. These tests use synthetic values, in-memory state, injected network functions, loopback app listeners and inert lifecycle doubles. They verify managed-injection refusal before DNS/network and direct-pinned challenge/event wiring, including retries and 410 handling; they do not verify a deployed callback or connect to a provider.
